# API 설계·검증

HTTP API·검색 구현이 요청된 작업에서 해당 항목만 적용한다. 기존 [작업 순서와 승인](../CODING_STANDARDS.md#작업-순서와-승인), [개인정보와 실행 경계](../CODING_STANDARDS.md#개인정보와-실행-경계)를 유지한다.

## 설계 기준

구현 전에 입력·응답·오류·호환성 계약을 문서화한다. 계약을 바꾸면 관련 동작의 실패를 먼저 확인하고 최소 구현으로 수정한다.

| 항목 | 설계 기준 | 핵심 검증 |
|---|---|---|
| 1. 버전과 호환성 | 버전 선택 방식, 파괴적 변경의 기준, 지원·전환·폐기 절차를 정한다. 같은 버전의 경로 뒤에서 계약을 조용히 바꾸지 않는다. | 기존 클라이언트의 요청·응답 계약과 전환 경로 |
| 2. 쓰기 멱등성 | 메서드의 멱등성을 지키고, 재시도로 부작용이 중복될 수 있는 쓰기에는 중복 방지 전략을 둔다. 멱등 키를 쓰면 사용자·테넌트·작업 범위, 보존 기간, 본문 불일치·동시 요청 처리를 정한다. | 순차·동시 재시도와 응답 유실 후 재시도에서 주문·청구 등의 중복 부작용 없음 |
| 3. 오류 모델 | HTTP 상태와 본문을 일치시키고 안정적인 오류 코드·요청 ID·재시도 가능 여부를 정한다. 공통 형식이 없으면 Problem Details를 검토한다. | 인증·권한·입력·충돌·제한·장애 응답의 상태·스키마와 재시도 안내 |
| 4. 외부 계약 | 내부 테이블·스택 트레이스·비밀값을 계약으로 노출하지 않는다. 필요한 안정적인 외부 식별자만 제공한다. ID가 숫자인지 UUID인지는 접근 권한 검사를 대신하지 않는다. | 응답 필드 제한, 오류의 내부 정보 노출, 다른 객체 ID로 접근 시도 |
| 5. 호출 단위 | 클라이언트 사용 흐름을 기준으로 응답을 설계하고 한 화면의 불필요한 연쇄 호출을 줄인다. 집계·배치에도 응답 크기와 처리량 상한을 둔다. | 대표 화면의 호출 수·응답 크기·지연과 부분 실패 |
| 6. 목록·필터 | 기본·최대 크기, 허용 필터, 안정적인 정렬과 동률 해소 키를 정한다. 대량·변경 빈도가 높은 목록은 커서를 우선 검토하고, 페이지 간 일관성을 문서화한다. | 상한 초과·잘못된 필터·커서, 동률 정렬, 추가·삭제 중 페이지 이동 |
| 7. 인증·권한 | 인증 외에 기능·객체·필드별 권한, 스코프와 테넌트 경계를 서버에서 검증한다. 클라이언트가 보낸 테넌트 ID나 커서를 권한의 근거로 신뢰하지 않는다. | 미인증·권한 부족·다른 사용자·다른 테넌트·권한 변경 후 접근 |
| 8. 자원 제한 | 헤더·본문 읽기와 전체 처리 시간, 본문 크기, 동시성·대기열·호출량 상한을 정한다. 취소·시간 초과를 하위 작업에 전달하고 과부하 시 거부·재시도 정책을 제공한다. | 느린 전송·큰 본문·동시 요청·시간 초과·취소에서 자원 회수와 제한 동작 |
| 9. 일관성 | 쓰기 후 읽기, 캐시·복제본 지연, 동시 갱신·충돌 처리와 허용되는 오래된 응답의 범위를 문서화한다. | 쓰기 직후 읽기, 캐시 무효화, 복제 지연과 동시 갱신 |
| 10. 관찰 가능성 | 검증된 요청 ID, 구조화된 로그, 경로별 지연·오류·제한 지표를 연결한다. 비밀값·개인정보를 로그에 남기지 않고 원시 ID·검색어를 지표 라벨로 쓰지 않는다. | 오류 추적 연결, 민감값 마스킹, 지표 라벨의 크기·종류 제한 |

멱등성과 재시도는 [HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2), 오류 형식은 [Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html), 객체 권한 검사는 [OWASP BOLA](https://github.com/OWASP/API-Security/blob/master/editions/2023/en/0xa1-broken-object-level-authorization.md)를 참고한다. 목록·계약 설계는 [Microsoft 서비스 설계 기준](https://github.com/microsoft/api-guidelines/blob/vNext/azure/ConsiderationsForServiceDesign.md)을 참고한다.

## 빈 검색어와 필터

- 검색어 누락·`null`·빈 문자열·공백만 있는 입력의 처리를 계약으로 정한다. 문서화한 정규화를 적용한 뒤 서버에서 검사한다.
- 검색 필수 경로는 기본적으로 유효하지 않은 검색어를 거부한다. 기존 계약이 0건 응답을 요구하면 빈 결과를 반환한다. 두 경우 모두 검색 조건을 없애거나 `LIKE '%%'`로 바꿔 전체 목록을 조회하지 않는다.
- 전체 목록이 필요하면 권한·페이지 크기가 제한된 별도의 명시적 동작으로 제공한다. 프런트엔드의 빈 입력 검사에만 의존하지 않는다.
- 인식하지 못한 필터·잘못된 커서를 조용히 무시해 조회 범위를 넓히지 않는다. 커서는 해당 권한·테넌트·필터·정렬 범위에서만 해석한다.

## 회귀 검증

- 검색 결과가 존재하는 테스트 데이터로 누락·빈 문자열·공백·해당 형식의 `null`을 각각 검사한다. 빈 테스트 데이터에서 우연히 0건이 나오는 검증을 피한다.
- 빈 검색어는 응답의 상태·내용뿐 아니라 전체 조회가 호출되지 않았는지도 확인한다. 유효한 검색어·일치 없음·최대 길이·특수문자 처리도 검증한다.
- 정상·실패·재시도·동시 요청과 권한 경계 중 변경에 해당하는 동작을 먼저 실패시키고 수정한다. DB 삭제·초기화에는 기존 사전 승인 규칙을 적용한다.
- 쿼리 수·캐시·지연을 개선하는 작업은 [성능 기준](performance.md)의 해당 절을 함께 적용한다. 실제 API 구현·실행을 검증하지 않았다면 기준 문서의 확인과 구분해 보고한다.
